## MemoEngine × MetaX C500

晶铁正式公开基于 **沐曦 C500 GPU 与 MXMACA 国产软件生态**的
**DeepSeek-V4-Flash 双 C500 本地部署方案与性能测试结果**。

目前，DeepSeek-V4-Flash 已在双沐曦 C500 环境下完成从模型加载、
异构推理到在线服务的完整链路验证，并完成单请求、多并发、
长序列及 128K 级上下文容量测试。

**MetaX C500 × 2** · **C1 52.93 tokens/s** · **C19 88.47 tokens/s** · **40/40 case 成功** · **128K 容量验证**

> **并发延迟说明**

> 单请求低排队压力下的平均 TTFT 为 **629 ms**。

本次公开结果同时报告吞吐与延迟指标，

## 6. MemoEngine 异构 MoE 推理架构

DeepSeek-V4-Flash 采用 MoE 架构，
专家权重规模较大。

在双 C500 环境下，
MemoEngine 通过 CPU 与 GPU 的异构协同，
对专家权重存储、专家计算以及运行时调度进行统一组织。

整体执行链路包括：

```text
DeepSeek-V4-Flash
        │
        ▼
      SGLang
        │
        ▼
     MemoEngine
        │
        ├── 模型权重组织
        ├── MoE 专家调度
        ├── CPU-GPU 异构计算
        ├── 数据传输与同步
        ├── 双卡任务协同
        ├── 图执行
        └── 长上下文资源管理
        │
        ▼
 MetaX C500 × 2
        │
        ▼
  Local Inference Service
```

---

### 6.1 基于沐曦国产生态的适配

围绕 DeepSeek-V4-Flash 在沐曦国产 GPU 环境中的实际运行需求，
MemoEngine 完成了多个关键链路的适配，包括：

- 模型权重加载与低精度计算路径；
- MoE 专家计算；
- 沐曦平台原生算子调用；
- CPU-GPU 数据传输；
- 异步计算与同步；
- 双卡执行与通信；
- 图执行与推测解码；
- 长上下文资源管理。

目前相关链路已在
**沐曦 C500 × 2 + MXMACA 国产软件生态**
环境下完成实际运行验证。

---

### 6.2 CPU-GPU 异构专家协同

MemoEngine 根据专家配置组织计算任务：

- GPU 侧负责高频、高密度专家计算；
- CPU 侧承载容量型及相应专家权重与计算任务；
- CPU 与 GPU 之间通过异步任务组织完成数据传输与计算协同；
- 推理过程中统一完成两侧结果同步与合并。

这种方式使大型 MoE 模型无需将全部专家权重同时驻留于 GPU 显存，
即可在双 C500 环境下完成完整推理。

---

### 6.3 双 NUMA 与 Rank-Local 组织

CPU 专家执行采用双 NUMA 资源组织。

每个 TP rank 维护本地的：

- CPU 专家集合；
- 权重视图；
- 执行队列；
- NUMA 本地内存；
- CPU/GPU 工作边界。

| 组织项 | 实现方式 |
| --- | --- |
| NUMA 池 | 2 个独立线程池，对应 NUMA 0 / 1 |
| TP Rank | 每个 rank 维护本地 CPU 专家集合与权重视图 |
| 内存访问 | 优先保持本地 NUMA 访问 |
| 任务队列 | 按专家任务组织 |
| 结果合并 | 本地 CPU/GPU 计算完成后进入跨卡协同 |

该设计主要用于减少跨 NUMA 访问和跨 rank 隐式等待。

---

### 6.4 多卡协同

在 TP2 环境下，
MemoEngine 对专家归属、权重视图、执行队列以及通信边界进行统一组织。

双卡不是简单复制相同计算，
而是使每个 rank 都承担明确的本地 CPU、GPU 与通信任务，
并最终完成两侧计算结果同步与合并。

---

### 6.5 图执行与推测解码

系统对稳定设备计算使用图执行降低重复调度开销，
同时对 CPU 专家任务以及跨阶段依赖保留明确的异步执行边界。

主模型路径与 draft / verify 路径统一管理：

- 推测状态；
- KV 状态；
- 设备计算；
- CPU 专家任务；
- 结果验证与状态更新。

推测解码因此作为完整推理执行链路的一部分运行。

## 10. 数据口径说明

为保证不同测试结果之间的口径一致，本文采用以下指标定义。

### Output Throughput

指测试期间实际生成的输出 tokens 数量除以对应测试时间：

```text
Output Throughput = Generated Output Tokens / Time
```

本文标题及主要性能数据均采用
**输出吞吐（Output Throughput）**
作为统一口径。

### TTFT

Time To First Token，
即从请求进入服务端开始，到生成首个输出 token 的时间。

### TPOT

Time Per Output Token，
用于描述首 token 生成后，持续生成阶段每个输出 token 的平均时间。

### 并发数据

C1、C3、C5 …… C19 表示测试时施加的不同客户端并发压力。

本文主要报告：

- 聚合输出吞吐；
- TTFT；
- TPOT；
- 正式测试成功数量。

### 长序列数据

每个长序列测试点独立记录：

- 输入长度；
- 输出长度；
- 输出吞吐；
- TTFT；
- TPOT。

### 128K 容量验证

128K 容量测试用于验证上下文配置与容量边界，
与长序列等长输入/输出性能测试分开统计。
